# TC11 表記ゆれチェック：ペア表と根拠

`meisai_checker/textcheck/variant_pairs.json` の各エントリは `source` 欄に根拠を持つ。
推奨表記は、根拠のあるものだけに付けている。

## 参考資料

| 資料 | URL | 用途 |
|---|---|---|
| 公用文作成の考え方（令和4年1月、文化審議会建議） | https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93651301_01.pdf | 仮名書きの原則（Ⅰ-1(2)(3)）、算用数字の「か所」（Ⅰ-1(1)）、長音、「等」「など」の扱い（Ⅱ-5） |
| 公用文における漢字使用等について（平成22年内閣訓令第1号） | https://www.bunka.go.jp/kokugo_nihongo/sisaku/joho/joho/kijun/sanko/koyobun/pdf/kunrei.pdf | 副詞・接続詞の漢字／仮名（１(2)イ・オ）、仮名で書く語句（１(2)キ）、送り仮名を省く186語（２(1)） |
| 「特許ライティングマニュアル」大幅改訂（Japio、2018年） | https://www.japio.or.jp/00yearbook/files/2018book/18_5_04.pdf | 参考（紹介記事。表記ゆれの個別規定は載っていない。民間の基準の参考として確認） |

## 方針

- 同一文書内の別表記の混在は、正誤を決めずに指摘する（`kind: mix`）。
- 推奨表記は、上記の資料で根拠が確認できたものだけに付ける。
- 官民で基準が割れているもの（など／等）や、使い分けの可能性があるもの
  （係る／かかる、更に／さらに、箇所／か所、一つ／1つ）は `severity: soft`（info）にする。
- 公用文の仮名書きの原則に反する旧表記（但し・出来る・〜の様に 等）は、
  混在の有無にかかわらず単独で info 指摘する（`kind: deprecated`）。
- 「行う／行なう」「表す／表わす」は、どちらを推奨とするかは保留（送り仮名の付け方・昭和48年内閣告示の
  確認待ち）。混在のみ指摘する。
- 建議は法令ではなく、訓令の運用方針を2022年に見直した文書である。特許庁の様式や審査基準が
  別の定めを置く場合はそちらを優先する。

## 長音の揺れ（ペア表とは別ロジック）

ユーザー／ユーザ、サーバー／サーバのような、語末の長音の有無の混在を検出する
（`check_long_vowel`、warning）。

- MeCab で名詞のカタカナ語を取り出し、語末の長音を除いた形が一致するものを同一語として扱う。
  複合語は MeCab が分割するので（ユーザーインタフェース→ユーザー＋インタフェース）語末だけを見れば足りる。
- 語中の長音（ビル／ビール）は別語なので対象外。語末の長音を除いた長さが2文字以下の語も対象外。
- 推奨表記は付けない。官は長音符号を使う原則（公用文作成の考え方 Ⅰ-1(3)エ、例：コンピューター）、
  技術文書の慣行は省略もあり、官民で割れているため。件数の多い側に寄せる。同数なら長音ありを残す。
- ペア表を明示しない通常の呼び出し（`analyze()`）のときだけ実行する。
  ユーザー上書きファイルに `"long_vowel": false` と書くと無効にできる。

## ユーザー上書き

`~/.meisai-checker/variant_pairs.json` に、同じ形式で `pairs` を書く。
`id` が一致すれば項目単位で上書き、新しい `id` なら追加、`"enabled": false` で無効化できる。
