# MPFクレーム認定リスク検出 — ルール設計書

**チェックID**: M7c  
**対応法条**: 特許法36条6項2号（明確性要件）  
**審査基準参照**: 第II部第2章第3節(2)a — 機能・特性等による発明特定事項  
**作成日**: 2026-05-18  
**ステータス**: 実装保留（LLMプロンプトとして代替実装済み）

---

## 1. 対象と目的

### 1.1 検出対象

「手段プラス機能（Means-Plus-Function, MPF）クレーム」認定リスクを持つ請求項を検出する。

日本特許法には米国35 USC 112(f)のような明文規定はないが、特許庁審査基準（第II部第2章第3節(2)a）は「機能・特性等によって発明特定事項を記載するときは、当該機能・特性等から当業者が実施できる程度に明確でなければならない」と定めており、以下の場合に明確性違反となる：

1. **機能語のみクレーム**: 「〜する手段」「〜する機構」等を用いて、対応する構造・材料・行為の記述なしに発明特定事項を特定しているケース
2. **過度に広い機能的記載**: 明細書の実施例によらなければ技術的内容が把握できないほど抽象的なケース

本チェック（M7c）は **請求項本文をスキャンして、MPFリスクが高い語句を含む請求項を抽出し、同一請求項に構造・材料・行為の記述が不足していればフラグを立てる** ことを目的とする。

### 1.2 誤検知の許容レベル

**実用的**（厳格 > 実用的 > 緩め）を選択する。理由：

- 特許明細書の文体は多様であり、「手段」が名称として正当に使われる場合が多い（例: 「記録手段」は実施例に具体的な構造があれば問題ない）
- 誤検知が多いと弁理士ユーザーに無視されるリスクが高い
- `level: 'warning'` と `level: 'info'` を使い分けることで、深刻度を伝える

誤検知率の目標: 精度 ≥ 70%（TP / (TP + FP)）を目安とし、除外ルールで調整する。

## 2. 要注意語句リスト（トリガーパターン）

### 2.1 パターン分類の考え方

MeCabトークン列を用いて「機能表現 + 後続する広義の概念語」という構造を検出する。具体的には：

- **機能表現**: 動詞の連体形（「〜する」「〜した」）または動詞句（「〜を行う」「〜を実行する」）
- **概念語**: 構造的含意を持たない広い名詞（「手段」「機構」「機能」「ユニット」等）

### 2.2 高リスクパターン（`level: 'warning'`）

これらは機能的表現 + 概念語の組み合わせであり、それ自体では構造が特定されない。

| # | テキストパターン | MeCabトークン条件 | 説明 |
|---|---------------|-----------------|------|
| H1 | `〜する手段` | `動詞(連体形) + [助詞?] + 名詞「手段」` | MPFクレームの典型表現 |
| H2 | `〜するための手段` | `動詞(連体形) + 助詞「ため」 + 助詞「の」 + 名詞「手段」` | H1の変形 |
| H3 | `〜する機構` | `動詞(連体形) + 名詞「機構」` | 構造記述なしの機構クレーム |
| H4 | `〜する機能を有する` | `動詞(連体形) + 名詞「機能」 + 助詞「を」 + 動詞「有する」の変形` | 機能そのものを発明特定事項とする場合 |
| H5 | `〜する機能を備える` | H4 の「有する」→「備える」変形 | 同上 |

> **正規表現の補完**: H1〜H5はMeCabトークン列でなく正規表現でも表現できる（後述の実装設計を参照）。初回実装は正規表現を優先し、誤検知が増えた段階でMeCabトークン列判定に切り替える。

### 2.3 中リスクパターン（`level: 'info'`）

「部/ユニット/モジュール」等は構造的含意を持つ場合もあるが、機能表現との組み合わせ次第では問題になり得る。

| # | テキストパターン | MeCabトークン条件 | 説明 |
|---|---------------|-----------------|------|
| M1 | `〜するユニット` | `動詞(連体形) + 名詞「ユニット」` | 日本語明細書では「部」より抽象的 |
| M2 | `〜するモジュール` | `動詞(連体形) + 名詞「モジュール」` | ソフトウェア分野で多用 |
| M3 | `〜を行う部` | `名詞句 + 助詞「を」 + 動詞「行う」 + 接尾辞「部」` | 「判定を行う部」等 |
| M4 | `〜を実行する手順` | `名詞句 + 助詞「を」 + 動詞「実行する」 + 名詞「手順」` | 方法クレームの機能的記載 |
| M5 | `〜するための回路` | `動詞(連体形) + ため + の + 名詞「回路」` | 回路構成が特定されていない場合 |

### 2.4 低リスクパターン（参考）

以下は構造的含意が強いため、デフォルトでは検出しない。除外ルールに用いる。

- `〜する装置` — 発明カテゴリ語であり、クレーム全体の主語として機能する
- `〜する部材` / `〜する部品` — 「部材」「部品」は物理的実体を示唆する
- `〜するデバイス` — 個別の電子素子を指すことが多い

## 3. 構造・材料・行為の記述チェックルール

MPFリスクフラグを立てた後、同一請求項に「十分な構造/材料/行為の記述」があれば **リスクを緩和** する。この判定は以下の3カテゴリで行う。

### 3.1 構造語の判定基準

正規表現またはキーワードリストで請求項本文を検索する。

**形状語**: 「板状」「円筒形（状）」「矩形」「箱型」「線状」「棒状」「膜状」「球状」「多角形」「テーパ形状」「L字形」「T字形」「U字形」

**寸法語**: 数値 + 単位のパターン（`\d+(\.\d+)?\s*(mm|μm|nm|cm|m|μ|inch|インチ)`）

**配置語**: 「に配置され」「に設けられ」「に形成され」「に取り付けられ」「に搭載され」「に固定され」「に積層され」「に埋め込まれ」

**接続語**: 「に接続され」「に接合され」「に連結され」「に係合され」「に嵌合され」「と当接し」「に固着され」「を介して連通し」

**数量語**: 「第1の〜と第2の〜」のような序数を含む並列構造（複数の異なる要素が明示されている）

### 3.2 材料語の判定基準

**組成表現**: 「からなる」「から形成される」「から構成される」「から製造される」

**材料名詞**: 「〜製」「〜材」「〜合金」「〜樹脂」「〜ガラス」「〜セラミック」「〜金属」「〜繊維」「〜フィルム」「〜コーティング」

**化学式・化合物名**: アルファベット+数字の組み合わせ（例: SiO2, Al2O3）、または「〜化合物」「〜ポリマー」

### 3.3 行為語の判定基準（主に方法クレーム）

**手順表現**: 「〜するステップ」「〜する工程」「〜するステップを含む」「〜する工程を有する」

**条件付き行為**: 「〜することにより」「〜した後に」「〜した結果として」

**動作の連鎖**: 複数の動詞句が「、」または「〜し、」で結ばれ、具体的な操作手順が記述されている

### 3.4 「記述が十分」と判定する条件

以下のいずれかを満たす場合、MPFリスクを **緩和** する（`level` を1段階下げるか警告を抑制）：

- **条件A（構造記述あり）**: 上記3.1のカテゴリのうち2種類以上が同一請求項中に存在する
- **条件B（材料記述あり）**: 上記3.2の材料語が1つ以上含まれる
- **条件C（行為記述あり、方法クレームの場合）**: 上記3.3の手順表現が2つ以上ある（方法クレームのみ適用）

いずれも満たさない場合は元の `level` で issue を発行する。

## 4. 除外・緩和条件（誤検知対策）

### 4.1 名称に構造が含意される除外語リスト

以下の語は技術的慣行上、構造的含意を持つため、直前の動詞連体形があっても検出対象から除外する。

```python
_MPF_EXCLUDE_NOUNS = frozenset({
    # 電気・電子部品
    'スイッチ', 'バルブ', 'センサ', 'センサー', 'モータ', 'モーター',
    'ポンプ', 'アクチュエータ', 'コイル', 'キャパシタ', 'トランジスタ',
    'ダイオード', 'レジスタ', '抵抗', 'コンデンサ', 'インダクタ',
    # 機械要素
    'ばね', 'バネ', 'スプリング', 'ギア', 'ギヤ', '歯車', 'ネジ',
    'ボルト', 'ナット', 'ピン', 'レール', 'ガイド', 'レバー',
    # 光学素子
    'レンズ', 'プリズム', 'ミラー', '鏡', 'フィルタ', 'フィルター',
    # 流体要素
    'ノズル', 'オリフィス', '弁',
    # 半導体・基板
    'トランジスタ', '基板', 'チップ', 'ウェハ',
})
```

これらの語が「〜する手段」等の後続の修飾語として現れる場合（例: 「温度を検出するセンサ」）は検出しない。

### 4.2 マルチクレームの扱い

マルチクレーム（複数請求項に従属）は既存の `check_dependency` で検出対象になっている。M7cでは追加のMPFチェックを行うが、マルチクレームを **除外しない**（MPFリスクは独立して存在するため）。

### 4.3 方法クレームの扱い

発明種別 `inv_types` が `'方法'` の場合：

- 「〜するステップ」「〜する工程」は行為クレームの正当な記述様式のため、H1〜H5の **検出対象から除外する**（ステップ・工程の後続語に「手段」等が来る場合は除外しない）
- 条件C（行為記述あり）の緩和ルールを優先適用する

```python
_METHOD_NOUNS = frozenset({'ステップ', '工程', '手順', '段階'})
```

### 4.4 発明主体語（クレーム末尾の主語）の扱い

日本語特許独立項はクレーム末尾に発明主体名詞が来る（head-final）。「〜する装置」「〜する方法」「〜するシステム」等の **クレーム末尾2〜5トークン内** に現れる名詞は、検出対象から除外する。

```python
_CLAIM_CATEGORY_NOUNS = frozenset({
    '装置', '方法', 'システム', 'プログラム', '製品', '記録媒体',
    '方式', 'プロセス', '製造方法', '処理方法', '通信方法',
})
```

### 4.5 「手段」が列挙・節タイトルとして使われる場合

「次の手段を採用する」「以下の手段により」等、クレーム本文ではなく明細書中の説明文脈で使われるパターンは、`sections['claims']` のみをチェック対象とすることで自動的に除外される。

## 5. 検出関数のインターフェース設計

### 5.1 ファイル配置

```
meisai_checker/patent/mpf.py  ← 新規作成
```

`patent/ambiguity.py` や `patent/clarity.py` と同じディレクトリに配置し、同じパターンで実装する。

### 5.2 関数シグネチャ

```python
def check_mpf(
    claims: dict[int, str],
    kinds: dict[int, str],
    inv_types: dict[int, str],
) -> list[dict[str, Any]]:
    """M7c: MPFクレーム認定リスク（機能的クレーム）を検出する。

    Args:
        claims:    {請求項番号: 本文テキスト}
        kinds:     {請求項番号: 種別文字列}  ← KIND_INDEPENDENT 等
        inv_types: {請求項番号: 発明種別}    ← '装置' | '方法' | 'システム' | 'プログラム' 等

    Returns:
        issues のリスト。各要素は dict:
            claim   : 請求項番号 (int)
            level   : 'warning' | 'info'
```

`dep_map` は不要（MPFは請求項単体で判定できる）。

### 5.5 正規表現実装方針

初回実装は正規表現ベースを採用し、精度が低下した際にMeCabトークン列判定に移行する。

```python
import re

# ── 高リスクパターン（H1〜H5）──
_MPF_HIGH_PATS: list[tuple[re.Pattern, str]] = [
    # H1: 〜する手段
    (re.compile(r'[^\s、。]{1,30}する手段', re.UNICODE), 'H1'),
    # H2: 〜するための手段
    (re.compile(r'[^\s、。]{1,30}するための手段', re.UNICODE), 'H2'),
    # H3: 〜する機構（構造語が伴わない場合）
    (re.compile(r'[^\s、。]{1,30}する機構', re.UNICODE), 'H3'),
    # H4: 〜する機能を有する
    (re.compile(r'[^\s、。]{1,30}する機能を有する', re.UNICODE), 'H4'),
    # H5: 〜する機能を備える
    (re.compile(r'[^\s、。]{1,30}する機能を備える', re.UNICODE), 'H5'),
]

# ── 中リスクパターン（M1〜M5）──
_MPF_MEDIUM_PATS: list[tuple[re.Pattern, str]] = [
    # M1: 〜するユニット
    (re.compile(r'[^\s、。]{1,30}するユニット', re.UNICODE), 'M1'),
    # M2: 〜するモジュール
    (re.compile(r'[^\s、。]{1,30}するモジュール', re.UNICODE), 'M2'),
    # M3: 〜を行う部（ただし「部」が接尾辞の場合）
    (re.compile(r'[^\s、。]{1,20}を(?:行う|実行する|処理する|実施する)部(?![材品品])', re.UNICODE), 'M3'),
    # M4: 〜を実行する手順
    (re.compile(r'[^\s、。]{1,30}を実行する手順', re.UNICODE), 'M4'),
    # M5: 〜するための回路
    (re.compile(r'[^\s、。]{1,30}するための回路', re.UNICODE), 'M5'),
]

# ── 構造語リスト（緩和判定用）──
_STRUCTURE_PATS: list[re.Pattern] = [
    # 形状語
    re.compile(r'板状|円筒形|矩形|箱型|線状|棒状|膜状|球状|テーパ|[LTUJV]字形', re.UNICODE),
    # 寸法語
    re.compile(r'\d+(\.\d+)?\s*(mm|μm|nm|cm|μ|inch|インチ)', re.UNICODE),
    # 配置語
    re.compile(r'に(?:配置|設けられ|形成|取り付けられ|搭載|固定|積層|埋め込まれ)', re.UNICODE),
    # 接続語
    re.compile(r'に(?:接続|接合|連結|係合|嵌合|固着)(?:され|する|した)', re.UNICODE),
    # 序数並列（構造の多様性を示す）
    re.compile(r'第[一二三1-9１-９]の.+第[二三四2-92-9２-４]の', re.UNICODE),
]

# ── 材料語リスト（緩和判定用）──
_MATERIAL_PATS: list[re.Pattern] = [
    re.compile(r'から(?:なる|形成される|構成される|製造される)', re.UNICODE),
    re.compile(r'[^\s、。]{1,10}(?:製|材|合金|樹脂|ガラス|セラミック|金属|繊維|フィルム)', re.UNICODE),
]
```

## 6. テストケース設計

### 6.1 検出すべきポジティブケース（5件）

**POS-1: 典型的な手段プラス機能クレーム（H1）**

```
請求項1：
データを圧縮する手段と、
圧縮されたデータを伝送する手段と、
伝送されたデータを伸張する手段とを有するデータ処理装置。
```
期待: `level='warning'`, `check='mpf_high'` が3件（または1件にまとめて）発生  
理由: 「圧縮する手段」「伝送する手段」「伸張する手段」いずれも構造記述なし

**POS-2: 機能を有する（H4）**

```
請求項2：
入力信号を増幅する機能を有する回路素子と、
増幅された信号を変換する機能を有する変換部とを備えた電子装置。
```
期待: `level='warning'` が2件  
理由: 「増幅する機能を有する回路素子」「変換する機能を有する変換部」は回路素子・変換部の内部構造が不明

**POS-3: モジュール（中リスク、M2）**

```
請求項5：
ユーザー認証を実行するモジュールと、
認証済みデータを管理するモジュールとを有するサーバ。
```
期待: `level='info'`, `check='mpf_medium'` が2件  
理由: 各モジュールのハードウェア/ソフトウェア構成が不明

**POS-4: ための手段（H2）**

```
請求項1：
振動を検出するためのセンサと、
検出結果を解析するための手段と、
解析結果を出力するための手段とを備えた計測装置。
```
期待: 「解析するための手段」「出力するための手段」で `warning` が2件  
（「センサ」は除外ルール4.1で除外される）

**POS-5: 機能を行う部（M3）**

```
請求項3：
入力データの前処理を行う部と、
前処理済みデータの推論を行う部と、
推論結果の後処理を行う部とを含む機械学習装置。
```
期待: `level='info'`, `check='mpf_medium'` が3件  
理由: 各「部」の処理手段（アルゴリズム・回路構成等）が不明

### 6.2 検出しないネガティブケース（5件）

**NEG-1: 構造記述が十分にある手段（緩和条件A適用）**

```
請求項1：
基板上に配置され、シリコン基板からなる第1の光検出素子と、
前記第1の光検出素子に隣接して設けられ、InGaAs層からなる第2の光検出素子と、
前記第1および第2の光検出素子からの信号を差動増幅する手段とを有する光センサ。
```
期待: 検出しない（「差動増幅する手段」はあるが、同一クレームに配置語・材料語・接続語・序数並列が複数存在するため緩和）

**NEG-2: 除外語リストのセンサ（除外ルール4.1適用）**

```
請求項2：
温度を検出するセンサと、
湿度を検出するセンサと、
```

## 8. 設計上の留意事項

### 8.1 false positive 発生時の対処

誤検知が多い場合は以下の順で対処する：

1. `_MPF_EXCLUDE_NOUNS` に語を追加する（最も低コスト）
2. `_has_structure_description()` の判定閾値を緩める（条件A〜Cのしきい値調整）
3. 正規表現を MeCab トークン列判定に切り替え（「する」の直前が動詞連体形か確認）
4. `level` を `'warning'` → `'info'` に下げて通知のみに変更

誤検知事例は `.github/ISSUE_TEMPLATE/false_detection.md` で収集し、一定数集まったら対処する方針（既存の FUGO_EXCLUDE_LIST と同様の運用）。

### 8.2 日本における MPF の法的位置づけ

本チェックは「MPFリスクの予防的通知」であり、自動的に法令違反を判定するものではない。メッセージ文には「リスクがあります」「検討してください」等の助言口調を用い、断定を避ける（`check_vague_range` の表現を参考にする）。

### 8.3 将来的な拡張
